# 공개 승인 전에 확인할 것 — 한 장 정리 (2026-10-17)

공지문(`/announcement`, `docs/free-pwa-release-announcement-draft.md`), 약관(`/terms`), 개인정보 처리방침(`/privacy`)을 읽고 승인하기 전에 무엇을 보면 되는지 정리한다. 앱을 **쓰는** 것과 **공개하는** 것은 다르다 — 쓰는 데는 이 문서가 필요 없고, 외부에 공개하기 전에만 필요하다.

## 0. 먼저 정할 것 — 누가 운영하는가
`src/lib/operator-info.ts`의 7칸이 비어 있어서 약관·방침 화면이 「배포 전 확정 필요」라고 말한다.

| 칸 | 정해야 하는 것 |
|---|---|
| 운영자(개인 또는 법인)명 | 개인으로 할지, 회사(법인)로 할지. **소속(LRQA) 규정상 가능한지 먼저 확인** — 겸업·이해충돌 규정 |
| 사업자등록번호 | 사업자가 아니면 「해당 없음」 |
| 주소 | 공개하기 어려우면 「요청 시 제공」 |
| 개인정보 보호책임자 | 이름 또는 직위(개인정보 보호법 제31조) |
| 관할 법원 | 전속 관할로 정할 법원 |
| 약관·방침 시행일 | 공개 예정일 |

문의 채널은 지금 `openbrain.main@gmail.com`으로 되어 있다. 개인 계정인지 공용 계정인지, 앞으로도 쓸 주소인지 확인한다.

## 1. 공지문 — 「말한 것이 사실인가」
공지는 사실과 다르면 가장 위험하다. 이번에 한 번 바로잡았다(PR #174). 승인하기 전에 아래를 직접 확인한다.

| 공지가 말하는 것 | 근거 / 확인 방법 |
|---|---|
| 입력 자료는 브라우저에 저장되고 서버로 보내지 않는다 | 서버가 받는 것은 무료 라이선스 등록(아래 §3), **문의 양식**(`/api/contact`), 업데이트 안내·공지 읽기뿐이다(운영자용 `admin`·`auth` 경로 별도). 서버 API는 `src/app/api/` 아래 `license/*`, `contact`, `announcements`, `update-manifest`, `admin`, `auth`(자동 점검 `verify:license-api`가 파일 구성을 확인). **직접 확인**: 브라우저 개발자도구 → 네트워크 탭에서 자료를 입력·저장·Export할 때 외부로 나가는 요청이 없는지 한 번 본다 |
| EU 템플릿은 편의용 사본이며 최신본을 보증하지 않는다 | 사실이다(2024-12-13판 내장). 제출 전에 최신판인지 EU 사이트에서 확인하는 일은 사용자 몫이라고 공지가 말한다 |
| 전력 배출계수는 한국·「목록에 없는 나라」 두 값만 내장 | 사실이다(관보 원문과 대조함). 라이선스 고지가 함께 나온다 |
| 검증·법률 자문·최종 제출 책임을 대체하지 않는다 | 약관 4항과 같다 |
| 철강 제품만, 한 프로젝트 = 한 해·한 사업장 | 사실이다 |
| 소스 저장소는 비공개, 번들은 브라우저로 내려간다 | 사실이다 |

공지에 **없는 것**: 무료 라이선스 등록이 **필수**이고 그때 이메일·회사명 등이 서버로 간다는 점은 공지 본문에 직접 적혀 있지 않고 약관 5항과 방침에만 있다. 「서버로 보내지 않는다」만 읽은 사용자가 등록 때 놀라지 않게 공지에도 한 줄 넣을지 정한다.

## 2. 약관(`/terms`) — 법무가 볼 곳
1. **책임 제한(4항)**: 「산정 결과와 제출 책임은 사용자에게 있다」, 보증 없음 — 약관규제법상 지나친 면책으로 무효가 되는 부분이 없는지.
2. **무료 라이선스 제한(5~6항)**: 약관 위반·무단 재배포 때 접근을 제한할 수 있다는 조항의 범위.
3. **내장 자료(3항, 이번에 추가)**: EU 템플릿·기본값·벤치마크는 EU 공식 자료, **전력 배출계수 두 값은 IEA 자료로 CC BY-NC-SA 4.0(비상업 목적만)**. 이 앱이 「비상업」인지, 컨설턴트가 유료 컨설팅에 쓰는 것이 걸리는지, 나중에 유료 판을 낼 때 어떻게 할지를 법무에 묻는다. 걸린다고 하면 두 값을 빼고 사용자가 직접 입력하게 되돌릴 수 있다(몇 줄 수정).
4. **준거법·관할(7항)**: 운영자 정보가 정해지면 채운다.

## 3. 개인정보 처리방침(`/privacy`) — 법무가 볼 곳
- **서버로 가는 개인정보**: 이메일, 회사명, 담당자명, 연락처, 국가, 업종(무료 라이선스 등록).
- **처리 위탁(전부 해외)**: Vercel(호스팅), Neon(라이선스 DB), Resend(키 이메일 발송).
- **물어볼 것**: 국외 이전 고지에 필요한 항목(이전받는 자·국가, 이전되는 항목, 이전 시기·방법, 이용 목적, 보유 기간, 거부 방법)이 방침에 모두 있는지, 처리 위탁 고지가 맞는지, 보유 기간(「라이선스가 유효한 동안」)과 파기 절차가 실제 동작과 같은지, 만 14세 미만 비수집 문구.
- **사실 확인(개발 쪽 몫)**: 정말 위 6개 항목만 보내는지, 삭제 요청을 받았을 때 관리자 화면에서 실제로 지울 수 있는지 — 필요하면 제가 확인해 드린다.
- **이번에 코드를 읽다가 찾은, 방침과 어긋날 수 있는 곳(승인 전에 정해야 한다)**
  1. **문의 양식이 방침에 없다.** 앱의 문의 창(`/api/contact`)은 이메일·회사명·담당자명·연락처·국가·업종·문의 유형·**문의 내용**·문의한 화면·앱 버전을 운영자 메일로 보낸다. 방침의 「수집하는 개인정보」는 라이선스 등록 항목만 적고 있다. 문의 양식의 수집 항목·목적·보유 기간을 방침에 넣거나, 문의를 메일 주소 안내로 바꾸는 둘 중 하나를 정한다.
  2. **메일 발송 업체.** 방침의 처리 위탁은 Resend이지만 코드는 `GMAIL_REFRESH_TOKEN`이 설정돼 있으면 **Google(Gmail API)** 로, 없으면 Resend로 보낸다. 실제 배포 환경(Vercel 환경변수)에서 어느 쪽을 쓰는지 확인해 방침의 위탁 업체를 맞춘다(둘 다 쓸 수 있으면 둘 다 적는다).
  3. 위 둘은 제가 고칠 수 있다 — 어느 쪽으로 할지(문구를 맞출지, 기능을 바꿀지)만 정해 주시면 된다.

## 4. Go/No-Go 기록(`docs/v0.1.0-beta-go-no-go-record.md`)을 채우는 순서
1. 운영자 정보 7칸을 정한다(§0).
2. 위 §1~3을 읽고 법무 검토를 받는다(최소한 본인이 끝까지 읽고 사실과 다른 곳이 없는지 확인).
3. 약관 초안과 공지문 초안 맨 위의 `Status:`를 승인 상태로 바꾼다(`LEGAL_REVIEW_APPROVED`, `OPERATOR_REVIEW_APPROVED`).
4. Go/No-Go 기록의 결정·결정일·검토자·검토한 커밋·공지 채널과 체크리스트 10줄에 Yes/No를 적는다.
5. `npm run release:status`가 `READY`, `npm run release:approval`이 통과하는지 확인한다.

2~5의 파일 수정과 명령 실행은 본인이 읽고 승인했다고 알려 주시면 제가 할 수 있다. 승인 판단 자체는 제가 대신하지 않는다.
