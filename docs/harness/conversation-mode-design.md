# 대화형 모드 설계안 (v4 작업 순서 6번) — 결정 전 초안

작성: 2026-10-05. 상태: **초안 — 사용자 결정 4건 대기(§7).** 코드는 아직 한 줄도 바뀌지 않았다.
근거: `ux-concept-v4.md` §2·§4·§14·§15·§16, 그리고 1~5번 구현(#91~#97)과 run19 회귀의 경험.

## 1. 무엇을 만드는가 — 한 문장

**지도 화면 옆에, 한 번에 질문 하나씩 묻는 별도 진입로를 둔다.** 답은 지금의 입력폼과 **같은 저장 로직**을 거쳐 같은 IndexedDB에 들어가고, 막대·지도·EU 파일은 그대로다. 언제든 지도 화면으로 넘어가도 값이 유지된다(원본이 IndexedDB 하나라 추가 작업 없음).

## 2. 지켜야 할 것 (v4 §14 + 이번 회귀의 교훈)

1. 엔진·EU Export·보고서·데이터 모델·`.cbam` 호환은 건드리지 않는다. 새 파일로만 짓는다.
2. `panels.tsx`를 질문 스키마로 뜯지 않는다(그 안의 수십 개 결함 수정과 소스를 글자로 읽는 검증 스크립트가 있다).
3. 기본 화면은 끝까지 지도 화면. 대화형은 별도 진입로이고, 검증이 끝나기 전에는 기본값으로 올리지 않는다.
4. 막대·지도는 자체 산술 금지 — 이미 있는 `SeeFlowBinding`·`buildCumulativeBar`·`buildMapFlow`를 그대로 쓴다. 대화형에도 같은 막대가 붙는다.
5. **「없는 값을 지어내지 않는다」** — run19에서 막대가 입력 없이 「100% 낮다」를 그린 것처럼, 새 화면은 입력이 덜 찬 상태를 정직하게 말해야 한다(부분 입력 안내를 그대로 재사용).
6. 단계 하나 = PR 하나, `npm run verify` 통과 후 머지, 입력 경로를 건드린 단계는 머지 뒤 씨밤이 회귀 1회.

## 3. 질문 순서와 재사용할 로직

원칙: **제품 → 생산량 → 구매 강재 → 연료 → 전력 → 같이 쓴 에너지 나누기** (큰 블록부터. v4 §10). 첫 질문 직후 막대에 EU 기본값 기둥이 선다(#96에서 이미 가능).

| 질문 | 담당자가 답하는 것 | 저장에 쓰는 기존 로직 | 새로 필요한 것 |
|---|---|---|---|
| 0 | 회사·공장 이름, 국가, 기간 | `validateInstallationDraft`·`buildInstallationPayload`·`validatePeriodDraft`·`buildPeriodPayload` (`guided-edit.ts`) | 없음 |
| 1 | 무엇을 만드시나요 → 제품군 → CN | `PRODUCT_FAMILY_PRESETS`·`suggestDetailPresetFromText`·`validateProductDraft`·`buildProductPayload` | 제품군 고르는 질문 화면만 |
| 2 | 제품별 생산량(t), 불량·스크랩 | **공정 생성이 `panels.tsx` 안에 인라인**(`createLocalItem('processes', …)`) — 순수 빌더 없음 | **새 순수 빌더**(`conversation-process.ts`). 필드 매핑이 패널과 갈라질 위험 → §5의 동등성 검사로 막는다 |
| 3 | 구매한 강재: 이름·CN·양·공급국가, 모르면 EU 기본값 | `validatePrecursorDraft`·`buildPrecursorCreate`, 기본값은 `findDefaultValueReference`·`resolveDefaultSeeForYear` | 질문 화면만 |
| 4 | 고지서 연료 | `GUIDED_STREAM_KINDS`·`createSourceStreamValidationErrors` — 생성은 `panels.tsx` 인라인 | 새 순수 빌더 |
| 5 | 전력 사용량 | `validateElectricityDraft`·`buildElectricityUpdate` | 질문 화면만 |
| 6 | 한 고지서를 여러 공정이 같이 쓰나요 | `electricity-allocation.ts`·`fuel-allocation.ts`·`measurable-heat.ts` 빌더, 현황 `energy-split-summary.ts` | 질문 화면만(복잡하면 지도 화면으로 넘기는 선택지) |
| 7 | 결과 확인 → 제출 | `buildCumulativeBar`·결과 요약, EU 파일은 8단계 로직 | 요약 화면만 |

즉 **새 순수 빌더는 둘(공정 생성·연료 생성)** 이고 나머지는 이미 순수 함수다. 공정·연료는 패널과 같은 필드를 두 번 적게 되므로 §5가 필수다.

## 4. 「모르겠어요」와 수정 경로

- 구매 강재 SEE → EU 기본값으로 채움(이미 있는 기능). 이후 공급사 요청서 흐름(#94)으로 이어진다.
- 나누는 기준 → 생산량 비율(기본), 열은 임시 채움 + 「[임시]」 표시(#90).
- 전력·연료 사용량 → **남의 공장 값을 추정하지 않는다.** 「나중에 입력」으로 받고 노드는 빗금, 막대는 부분 입력 안내(#97)를 그대로 낸다.
- 수정: 답마다 칩으로 남기고, 칩을 누르면 그 질문만 다시 연다. 입력폼 모드(지도)에서 고친 값도 칩에 반영된다(원본이 같다).
- 지원하지 않는 것(열 수출·폐가스·자가발전 차감)이 나오면 값을 받아 계산하는 척하지 않고 「현재 버전에서 지원하지 않습니다」(PR #77 원칙).

## 5. 「같은 결과」를 어떻게 보장하나 (이 모드의 핵심 검사)

대화형이 입력폼과 **같은 SEE·같은 EU 파일**을 낸다는 것을 두 겹으로 잠근다.

1. **동등성 검사(`verify-conversation-equivalence.mjs`)**: 같은 자료(대일기업 기준선)를 ① 입력폼 빌더 경로 ② 대화형 빌더 경로로 각각 저장한 결과 레코드를 필드 단위로 비교한다. 새 빌더(공정·연료)가 패널과 어긋나면 여기서 깨진다.
2. **회귀(씨밤이)**: 두 경로로 같은 자료를 넣어 EU 사본의 셀을 대조한다(run19에서 한 방식 — 다른 셀 0개).
3. 구조 검사: 새 파일에 `createLocalItem`을 직접 쓰지 못하게 한다(모든 쓰기는 빌더를 거친 한 함수로).

## 6. 쪼개는 순서 (한 단계 = PR 하나, 어디서 멈춰도 앱은 그대로)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| S1 | 진입로 `/talk`(가칭) 뼈대 + 질문 0~1(사업장·기간·제품군→CN) + 막대 | 질문 두 개에 답하면 EU 기본값 기둥이 서고, 지도 화면으로 넘어가도 값이 그대로 |
| S2 | 질문 2(생산량) + 새 공정 빌더 + 동등성 검사 | 공정 저장 결과가 입력폼과 필드 단위 동일 |
| S3 | 질문 3(구매 강재, 모르겠어요→EU 기본값) | 기본값 채움 값이 지도 6단계와 같음 |
| S4 | 질문 4~5(연료·전력) + 새 연료 빌더 | 기준 SEE가 입력폼과 같음 |
| S5 | 질문 6(에너지 나누기) · 결과 요약 · 수정 칩 | 대일기업 기준선을 대화형으로 재현해 3.764 |

S1~S2만 하고 멈춰도 「제품만 넣어도 기본값이 보이는 시작 경험」이 남는다.

## 7. 결정이 필요한 것 (이 문서가 멈추는 곳)

1. **대화형을 지금 만들 것인가?** v4 §16-3은 「5단계까지 해본 뒤 결정」이었다. 5단계까지 끝났고, 시작 안내(#95)·첫 답 막대(#96)로 「처음 사용자」 경험이 이미 상당히 좋아졌다. 대화형은 위험이 가장 높은 항목이라 **효과 대비 비용**을 사용자가 판단해야 한다. 추천: 하되 S1~S2에서 멈출 수 있게 쪼개 시험한다.
2. **진입로와 이름**: 시작 안내 카드에 「질문에 답만 하면 됩니다」 카드를 더할지(기본 경로는 그대로 지도), 별도 주소만 둘지.
3. **AI 사용 여부**(v4 §16-1): **AI 끄기 상태에서 모든 질문이 동작하는 것이 이 설계의 전제**다. AI는 나중에 「자유 문장 → 칩」 어댑터로 얹는 것이고, 비용 부담 주체(운영자/사용자 키/유상판)는 이 결정이 날 때까지 보류해도 대화형은 만들 수 있다. 지금 AI를 같이 결정할 필요가 있는가?
4. **첫 범위**: 철강 가공업체(구매 강재 + 연료 + 전력)만으로 시작해도 되는가(제품군 `wire`·`fastener` 등 `product-family-presets.ts`의 프리셋). 고로 일관제철은 앱 범위 밖이다(메모리: 지원 범위 철강만).

## 8. 하지 않는 것

- 자유 대화형 챗봇(문장 해석)·AI 호출·외부 전송 — 이 설계에 없다.
- `panels.tsx` 분해·엔진/Export/보고서 수정.
- 다제품·다공정의 대화형 완결(첫 제품 한 개까지만; 나머지는 입력폼으로 넘겨 복제 — v4 §4).
