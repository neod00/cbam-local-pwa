## 0. 한 줄 정의

쇳물을 만들지 않는 중소·중견 **철강 가공업체** 담당자가 **자기에게 맞는 방식을 골라** 자사 숫자만 넣으면, 답할 때마다 CBAM 배출량이 눈앞에서 쌓여가고, 마지막에 EU 수입업자 제출용 서류가 완성되어 나오는 도구.

**산정은 수단, 서류가 목적.**

**[v4]** 범위는 철강만이다. 타 품목군·고로 일관제철·Mt급 전사 통합은 미지원(`docs/harness/target-segment-and-complexity.md`). 컨셉의 모든 예시·공정 맵·질문은 "강재를 사다 가공하는 공장"을 기준으로 쓴다.

## 1. 바뀌지 않는 다섯 기둥

| 기둥 | 내용 |
|---|---|
| 책임 분리 | 담당자는 고지서·생산일지·자재 명세서의 숫자만 답한다. 배출계수, EU 기본값, 할당, 경계 판정, 직접/간접 구분, 규제 용어, 신고 양식 매핑은 전부 앱 책임 |
| 고르는 방식 | 입력폼/대화형 · AI 끔/켬 · 실무자/입문자. 프리셋 카드로 시작, 언제든 전환, 입력값 유지. 어떤 조합이든 **같은 엔진 · 같은 산출물** |
| 보상 구조 | "얼마나 남았나"(진행률)가 아니라 **"내 숫자가 얼마나 믿을 만해졌나"** 를 보여준다. 실시간 막대와 살아 움직이는 공정 맵은 장식이 아니라 **이 제품의 정체성**이다. 대화형 모드는 "처음이에요" 사용자의 주 진입로다 |
| 막히는 곳에서 끌고 가기 | 모든 질문에 "모르겠어요". 전구물질은 기본값으로 먼저 계산을 끝내고 → 공급업체 요청 양식 생성 → 회신 오면 그 값만 교체. 모든 값의 출처 태그가 보고서까지 이어진다 |
| 넘지 않는 선 | **AI는 산정식에 절대 개입하지 않는다.** 계산은 100% 룰 기반, 같은 입력이면 항상 같은 결과. 기본은 로컬(외부 전송 없음) |

## 2. 3축 모드 선택

담당자마다 성향·숙련도·보안환경이 다르다. 하나의 정답을 강요하지 않는다.

| 축 | 선택지 | 결정 기준 |
|---|---|---|
| 입력 방식 | 입력폼 모드 / 대화형 모드 | 업무 성향 |
| AI 사용 | AI 끄기(로컬) / AI 켜기(API) | 보안 정책·편의 |
| 설명 수준 | 실무자 모드 / 입문자 모드 | CBAM 이해도 |

3축 독립 조합 = 8가지. 모든 조합이 동일한 산정 엔진과 동일한 산출물로 수렴한다.

### 선택이 부담이 되지 않게 (반드시 지킬 것)

첫 화면에서 세 번 연속 물으면 아무것도 모르는 상태에서 세 번 판단해야 한다. 이탈이 가장 큰 지점이다.

- **기본 프리셋을 카드로 제시**하고, 세부 3축은 "직접 설정" 링크 뒤로 숨긴다.

| 프리셋 | 조합 | 카드 문구 |
|---|---|---|
| 처음이에요 | 대화형 + 입문자 + AI 선택(기본 끔) | 질문에 답만 하면 됩니다 |
| 해본 적 있어요 | 입력폼 + 실무자 + AI 끔 | 항목별로 바로 입력합니다 |
| 직접 설정 | 3축 개별 지정 | — |

- **모든 모드는 작업 중 언제든 전환 가능. 입력값은 그대로 유지.** 이 사실을 시작 화면과 전환 버튼 옆에 한 줄로 명시한다 → "잘못 고르면 어쩌지" 부담 제거.
- 설명 수준은 우측 상단 토글로 상시 노출. 한 항목만 어려울 때 그 자리에서 켜고 끈다.

**[v4]** "전환해도 입력값 유지"는 이 앱에서 추가 작업 없이 성립한다 — 모든 값의 원본이 IndexedDB 하나(`src/lib/local-db.ts`)이고 화면은 그것을 읽어 그릴 뿐이다. 그래서 "모드 상태 레이어를 먼저 깔지 않으면 전면 재작업"이라는 원안의 우려는 해당하지 않는다(§12 작업 순서 참조).

## 3. 입력폼 모드 — 지금의 지도 화면을 유지·강화

**지도가 주역이다.** 좌측 8단계 지도 + 우측 입력 영역.

- 좌측 지도: 상시 노출, 8단계 조망, 클릭으로 자유 이동
- 지나온 단계 체크 / 현재 단계 강조 / 남은 단계 흐리게
- 우측: 한 단계 안에서도 의미 단위로 묶어 분할. 한 단계 = 한 화면, 스크롤 최소화
- 하단 고정: 실시간 산정 시각화 패널(§6)

전체를 조망하며 자기 페이스로 오가고 싶은 담당자, 자료가 다 준비된 담당자에게 적합.

**[v4]** 이 모드는 **이미 있다** — 기본 화면인 `src/components/guided/GuidedWorkspace.tsx`(지도 `GuidedMap.tsx` + 패널 `panels.tsx`)가 곧 입력폼 모드다. 새로 만들지 않고 막대·출처 표시·설명 토글을 **덧붙인다**.

## 4. 대화형 모드

앱이 한 번에 하나씩 묻고 담당자는 답만 한다.

- 규제 용어로 묻지 않는다. "간접배출 활동량" ❌ → "작년 한 해 전기를 얼마나 쓰셨나요? 한전 고지서 숫자면 됩니다" ⭕
- 판단이 필요한 질문은 반드시 객관식. 특히 나누는 기준(할당)은 자유입력 금지 → 선택하면 앱이 계산, 담당자는 확인만
- 모든 질문에 **"모르겠어요"** 버튼 필수
- **하이브리드 필수** — BOM 20줄을 대화창으로 받으면 실패한다

| 성격 | 처리 | 예시 |
|---|---|---|
| 판단·분기 | 대화 객관식 | 나누는 기준, 공정 구성, 구매 강재 유무 |
| 단일 수치 | 대화 숫자 입력 | 전력 사용량, 생산 기간 |
| 반복 수치 | 대화 안에서 열리는 인라인 표 패널 | 제품별 생산량, 연료 종류별 사용량 |
| 대량 데이터 | 해당 질문 안의 엑셀 업로드 버튼 | 다품목 실적, 자재 전체 |

표 패널은 대화 흐름 안에서 열리고 닫으면 대화가 이어진다. 별도 화면으로 튕기지 않는다.

### 수정 경로 — 대화형의 최대 약점, 반드시 해결

- 답변값은 대화 로그에 칩으로 남는다. `전력 사용량 · 1,240,000 kWh ✎`
- 칩 클릭 → 인라인 수정 → 산정 즉시 재계산
- 수정이 후속 답변에 영향을 주면 **해당 항목만 재질문** (전체 재시작 금지)

### [v4] 대화형의 범위와 규칙

- **범위 = 첫 제품 한 개를 끝까지 완결.** 다제품·다공정은 입력폼 모드로 전환해 복제한다(전환해도 값 유지). 앱 타깃 문서의 결론("한 제품 위저드 → 나머지 복제")과 같다.
- **객관식 선택지는 엔진이 이미 지원하는 값에 맞춘다.** 엔진을 바꾸지 않는다.
  - 제품 간 배분: 생산량 기준(`MASS`, 기본값) / 사용자 지정(`MANUAL`, 사유 필수)
  - 공용 계량기 나누기: 보조계량기 / 생산량이 기본 선택지. 가동시간·설비용량·기타는 엔진에 있으나(`SourceStreamSharedMeter.basis`) 규정 근거 확인이 필요하다 — §8-1 참조
- **"모르겠어요" 처리 규칙**
  - 전구물질 SEE → EU 기본값으로 채움(이미 있는 기능)
  - 나누는 기준 → 생산량 기준을 기본으로
  - 전력·연료 사용량 → 남의 공장 사용량을 추정할 근거가 없다. **"나중에 입력"** 으로 받고, 노드는 빗금, 할 일 목록에 남긴다
- **지원하지 않는 것은 묻되 정직하게 말한다.** 밖에서 산 스팀·온수(측정가능열)는 PR #81(2026-09 말)부터 지원한다(`src/lib/measurable-heat.ts`, 식 52·55의 EmH,imp). 열 수출·폐가스·자가발전 차감은 여전히 미지원이다(`ALLOCATION_RULES.ADJUSTMENTS`). 미지원 항목에 "예"가 나오면 값을 받아 계산하는 척하지 말고 「현재 버전에서 지원하지 않습니다」로 안내한다(PR #77과 같은 원칙).
- **첫 질문은 "무엇을 만드시나요"(제품군 → CN)** — 이유는 §6·§8.

## 5. 대화형 모드의 지도 — 살아 움직이는 공정 맵

대화형에서도 지도를 버리지 않는다. **형태와 거동을 바꾼다.** 입력폼의 지도가 "목차"라면, 대화형의 지도는 **공정이 실제로 연결되어가는 다이어그램**이다.

```
[구매 강재(전구물질)] ─┐
                       ├→ [가공 공정] → [제품] → ÷ 생산량 → [결과] → [EU 문서]
[연료] ────────────────┤
[전력] ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┘   (점선 = 보고용 흐름, §8)
```

### 거동 — 대화 한 턴마다 반응

| 상태 | 표현 |
|---|---|
| 아직 안 물어본 노드 | 아웃라인만, 저채도 |
| 지금 묻고 있는 노드 | 부드러운 펄스 글로우, 대화 말풍선과 동일 액센트 컬러 |
| 답변 완료 노드 | 채워짐 + 엣지에 흐름 애니메이션(점선이 흐르는 형태) |
| "모르겠어요"·기본값 노드 | 채워지되 빗금 패턴 + 점선 테두리 |

- 엣지 두께 = 해당 경로의 배출 기여도. 답변이 쌓일수록 굵기가 재조정되어 **어디가 배출 핵심인지가 저절로 드러난다**
- 노드 호버 시 해당 값·출처·기여도 툴팁
- 답변 확정 순간 해당 노드 → 산정 패널 막대의 해당 블록으로 **빛 입자가 이동**하는 미세 트랜지션(200~300ms). 입력이 결과로 변환되는 인과를 각인

### 톤

- 애니메이션은 절제. ease-out, 200~400ms. 튀거나 바운스 금지
- 장식적 파티클·이모지·과한 채도 금지. 엔지니어링 다이어그램의 정확성을 유지한 채 상태 전이만 부드럽게
- 노드 간격·정렬은 그리드 기반. 손그림이 아니라 **설계도면 느낌**

### [v4]

- 뼈대는 이미 있다. `GuidedMap.tsx`가 노드-엣지 SVG 다이어그램이고(제품→공정→①연료 ②전력 ③전구물질→÷생산량→결과→문서), 현재 단계 펄스·완료 팝·`prefers-reduced-motion` 대응이 들어 있다. 새로 짓지 않고 **강화**한다.
- 엣지 두께에 쓸 값은 `src/lib/see-flow.ts`의 `SeeFlowBinding`이 이미 집계한다(①직접 · ②자체 전력 · ③전구물질 직접/간접, tCO₂e).
- 공정 구성은 자유 작도가 아니라 **철강 제품군 템플릿**에서 고른다 — `src/lib/product-family-presets.ts`가 제품군별 공정명·생산경로·전구물질 후보를 갖고 있다.
- **전력 엣지는 배출량만큼 굵게 그리지 않는다.** 점선 등 보조 표현으로 "보고용 흐름"임을 구분한다(§8).
- 빛 입자 이동은 지도와 막대가 좌표를 공유해야 해서 손이 많이 간다 → 지도 강화 작업의 마지막 항목.

## 6. 실시간 산정 시각화 — 두 모드 공통, 이 앱의 핵심 장치

시각적 완성도가 곧 제품 신뢰도로 읽히는 부분.

### [v4] 신뢰구간 밴드 → "3단 사다리 + 실측 비율"

원안의 오차 밴드(상한·하한 음영)는 **쓰지 않는다.** 상·하한을 정할 통계가 없다 — EU 기본값은 확률분포가 아니라 일부러 높게 잡은 보수적 값이고, 전력·연료 사용량에는 기본값 자체가 없다. 근거 없는 구간을 그리면 검증인의 "이 밴드는 어떻게 계산했나요?"에 답할 수 없고, 재현성 원칙(§7)과도 어긋난다.

대신 CBAM 규정에는 **그대로 신고할 수 있는 상태가 세 단계** 있다. 원안의 "중간에 멈춰도 쓸 수 있는 결과가 존재한다"는 비유가 아니라 규정상 사실이다.

1. 전부 EU 기본값 (아무것도 안 넣으면 이 숫자)
2. 자사 실측 + 전구물질 기본값
3. 전부 실측

### 구성

- **회색 기둥**: 이 제품 CN의 EU 기본값(연도별 mark-up 포함). "아무것도 안 넣으면 이 숫자로 신고됩니다"
- **실색 기둥**: 내 값. 세로 누적, 블록 = **연료(자체 직접배출) / 전구물질 직접분**. 공정 직접배출은 타깃 업체(가공업)에서 거의 0이므로 값이 있을 때만 블록으로 나온다
- **전력 조각**: 본체에서 떼어 윤곽선만 있는 「보고용」 조각으로 그린다(자체 전력 + 전구물질 간접분). 대형 수치에 넣지 않는다. 간접 포함 품목이면 본체에 합쳐 그린다(§8)
- **하단 대형 수치: 기준 SEE** (tCO₂e / t 제품). 총 SEE는 작은 보조 수치
- **실측 비율 N%**: 인증서 기준 부분 중 실측 기반이 차지하는 몫. 전력을 넣었다고 이 비율이 오르면 안 된다
- 두 기둥의 차이 = 실측으로 줄인 양 = 곧 인증서 비용 차이. 밴드 수축보다 보상이 더 직접적이다
- 벤치마크 라인은 "업종 평균"이 아니라 이 **EU 기본값**이다(업종 평균 데이터는 앱에 없다)

### 동작

1. 첫 질문(제품군 → CN)에 답하는 순간 회색 기둥 전체가 나타난다 — **첫 답에 막대가 움직인다**
2. 실제 값을 답할 때마다 실색 기둥에 블록이 쌓이고 실측 비율이 오른다
3. "모르겠어요"·기본값 항목은 빗금 유지
4. 전량 실측 시 막대 전체 실색, 실측 비율 100%
5. CN이 없거나 판정 불가면 대형 수치 자리에 "—"와 "제품 CN을 입력해 주세요" — 판정이 안 된 제품에 숫자를 내놓지 않는다

### 왜 이 방식인가

담당자는 "몇 단계 남았나"보다 "내 숫자가 얼마나 믿을 만한가"에 반응한다. 진행률 바는 남은 노동량을 보여주지만, 이 장치는 **축적된 성과**를 보여준다. 중간에 멈춰도 쓸 수 있는 결과가 존재한다는 사실이 시각적으로 보장된다.

### 시각 품질 요구사항 — 컨설팅 리포트 수준

**색**
- 블록은 단일 색상의 명도 계열(monochromatic ramp) + 전구물질만 보색 액센트. 무지개 팔레트 금지
- 회색 기둥·보고용 조각은 테두리/저채도로 구분. 배경은 무채색 저채도. 데이터가 유일한 채도 소스

**타이포**
- 수치는 tabular figures(등폭 숫자) 필수 — 값이 바뀔 때 자릿수가 흔들리지 않게
- 메인 수치 / 단위 / 블록 라벨 3단 위계. 라벨은 소문자 트래킹 확장

**모션**
- 값 변경 시 막대는 높이 보간 300ms ease-out, 숫자는 카운트업 롤링
- 실측 비율 갱신은 250ms 딜레이 후 → 인과가 순차적으로 읽힌다
- 동시 애니메이션 금지. 막대 → 비율 → 수치 순서로 계단식

**부가 요소**
- 블록 호버 시 절대값·비중·출처(실측/기본값) 툴팁
- 값 출처 범례 항상 노출: 실측 / 기본값 / 미입력

### [v4] 구현 제약

- 막대는 **자체 산술을 하지 않는다.** `SeeFlowBinding`(집계)과 `describeSeeFlowIndirect`(문안)만 읽는다. 이 앱은 간접배출 단정 문구가 화면마다 재발한 이력이 있다.
- 저장할 때마다 엔진이 전체를 다시 계산하는 구조(`GuidedWorkspace.tsx`의 `reload` → `calculateLocalResults`)가 이미 있어 "답할 때마다 실시간"은 구조적으로 성립한다.
- 차트 라이브러리 의존성이 없다. 지도처럼 직접 그린 SVG/CSS로 만든다.
- 다공정·다기간에서는 기존 공정 탭·기간 선택(`selectedProcessId`, 보고기간)을 그대로 따른다.
- 시각 토큰은 `DESIGN.md`(teal 계열)와 `npm run verify:design-system` 게이트가 있다 — 단색 명도 계열 요구와 맞춰 조정이 필요하다(§13 미결).

## 7. AI 사용 축 — 끄기 / 켜기

### 절대 원칙

**AI는 산정식에 절대 개입하지 않는다.** 배출계수 적용, 할당 계산, 경계 판정은 100% 룰 기반. 두 모드의 산정 결과는 동일한 입력에 대해 항상 동일하다. 규제 대응 도구에서 계산의 재현성은 타협 불가. AI는 **입력을 돕고 해석을 돕는 보조 계층**으로만 존재한다.

### AI 끄기 (로컬) — 기본값

- 대화형도 사전 정의된 결정 트리로 완전 동작. AI 없이 전 기능 사용 가능
- 외부 전송 없음. 생산량·에너지 사용량은 민감 데이터이고, 보안 정책상 외부 API를 못 쓰는 곳이 실제로 많다
- 담당자가 아무 판단 없이 시작해도 안전해야 하므로 이것이 기본값

### AI 켜기 (API)

| 기능 | 내용 |
|---|---|
| 용어 실시간 풀이 | "이게 무슨 뜻이죠?" 자유 질문 대응 |
| 엑셀 컬럼 매핑 | 제각각인 헤더를 자동 인식 → 매핑 단계 생략 |
| 자유서술 해석 | "선재를 사다 신선하고 도금합니다" → 공정 구조 초안 |
| 공급업체 회신 파싱 | PDF·메일 본문에서 전구물질 배출량 추출 |
| 이상치 설명 | 룰이 잡아낸 이상치에 대해 "왜 이상한지" 설명 + 확인할 지점 |
| 요약문 초안 | 보고서 서술 부분 초안(수치는 엔진 값 고정) |

### 전환 UI

- 상단 상태 칩 상시 노출: `AI 보조 · 꺼짐` / `AI 보조 · 켜짐`
- 켤 때 1회 고지: 어떤 데이터가 전송되는지, 산정 결과에는 영향이 없다는 점
- AI가 채운 값은 **별도 표식**. 담당자 확인 전까지 잠정, 확정 클릭 시에만 실측으로 승격
- API 실패 시 룰 기반으로 자동 폴백. 작업 중단 없음

### [v4]

- **도입 순서 = 회사 데이터가 덜 나가는 것부터**: ① 용어 풀이(회사 데이터 0) → ② 엑셀 헤더 매핑(헤더만 전송) → ③ 공정 서술 해석 → ④ 공급사 PDF 파싱(제3자 기밀이 나간다).
- **표준 양식 회신은 AI가 필요 없다.** 공급업체가 EU Communication Template으로 회신하면, 앱이 이미 EU 엑셀을 읽으므로 룰로 파싱한다. AI 파싱은 PDF·메일 본문에만.
- **제품 약속과의 정합**: 앱 곳곳(16개 파일)과 약관·개인정보 안내에 "서버로 전송하지 않습니다"가 적혀 있다. 데이터 안전 원칙(`docs/harness/data-safety.md`)은 "기본은 로컬, 예외는 옵트인 + 문서화"라서 "기본 끔 + 켤 때 고지"와 충돌하지 않지만, AI 켜기를 출시하려면 그 문구들을 함께 고쳐야 한다.
- 기술적으로는 쉽다(API 라우트 구조가 이미 있다). **API 비용을 누가 부담하는지는 미결**(§13). 그래서 맨 마지막 단계다.

## 8. [v4] 철강의 직접배출 규칙 — 컨셉 전체에 걸리는 제약

앱은 EU 공식 Communication Template(2024-12-13판)의 확정기간 간접배출 관련성 표를 **조회**해 제품별로 판정한다(`src/lib/cbam-product-rules.ts`, `src/lib/cn-master.generated.ts`).

| 품목군 | 확정기간 간접배출 |
|---|---|
| 철강 제품(CN 72·73 가공품) · 조강 · 선철 · DRI · 합금철 | 직접배출만 |
| 소결광(2601 12 00) | 간접 포함 (앱 지원 범위 밖) |

- **"계산하지 않는다"가 아니라 "인증서 기준에서 빠진다".** 앱은 전력 입력을 받아 간접 SEE를 「보고용」으로 따로 계산한다(EU 템플릿에 적는 칸이 있다). 그래서 **기준 SEE**(인증서 기준)와 **총 SEE**(검토용) 두 값이 있다.
- **전구물질의 간접분도 같이 빠진다.** 기준 SEE = 자체 직접배출 + 전구물질의 직접분.
- 제품별 3상태(포함 / 인증서 산정 제외 / 판정 불가), 여러 제품을 모은 집계는 4상태(+혼재). 표시 문구는 반드시 `describeSeeFlowIndirect`(`src/lib/see-flow.ts`)에서 받는다.
- **"철강은 빠집니다" 같은 고정 단정 문구는 금지** — `npm run verify:ui-claims`가 소스 전체에서 막는다. "Annex II direct-only"라는 표현도 금지(등재를 확인하지 못했다. 확인된 사실은 "EU 공식 CN 목록상 간접배출 비관련"뿐).
- 컨셉에 미치는 영향: 막대 본체·대형 수치(§6), 전력 엣지(§5), 첫 질문은 전력이 아님(§4·§10), 실측 비율의 분모(§6).
- 덤: 철강에서는 전력이 인증서 비용에 영향을 주지 않으므로, 대화형에서 전력 배출계수 출처(계통평균·PPA·자가발전 등)의 어려운 분기를 "고지서 kWh만 입력" 수준으로 줄일 수 있다. 정밀 입력은 입력폼 모드에 남긴다.

## 8-1. [v4] 귀속·배분 — 공장 전체 에너지를 제품 몫으로 나누기 (2026-10-05 원문 대조)

고지서는 공장 전체 값이고 CBAM은 제품(생산공정)별로 배출을 따진다. 여러 제품(CBAM 대상·비대상)을 만드는 공장에서는 이 나누기가 결과를 좌우한다. **작업실에서 독립된 단계로 보여야 한다** — 목업 「2-1 · 같이 쓴 에너지 나누기」 참조. 원안 v3의 "할당 방법은 자유입력 금지, 객관식 선택 후 앱이 계산, 담당자는 확인만"이 여기에 해당한다.

### 규정이 정한 것 (Implementing Regulation (EU) 2025/2547, 원문: `CBAM_documents/EU Verification/OJ_L_202502547_EN_TXT.pdf`)

| 조항 | 내용 |
|---|---|
| Article 4(1)·(2) | 생산공정은 「같은 기능단위」의 재화 단위로 잡는다. 기능단위 = 같은 CN 코드의 생산 톤수 |
| Article 4(6) | 같은 기능단위(CN)를 여러 생산경로로 만들어도 생산공정은 하나 |
| Article 4(8) | 기능단위가 다른 재화를 같은 공정으로 만들면 「단일 다기능 생산공정」으로 묶을 수 있고, 이때 부속서 III A.2로 귀속한다 |
| 부속서 II A.4 | 철강·알루미늄 제품에서 크기·형상만 다르고 전구물질(종류·양·비율)이 같은 재화들은 CN이 달라도 **반드시** 단일 다기능 생산공정으로 묶는다 |
| 부속서 III A.1 | 공정별 측정값이 있으면 그 값을 쓰고, 합계가 사업장 전체와 다르면 정합계수(RecF = 전체 ÷ 공정 합계, 식 41·42)로 맞춘다 |
| 부속서 III A.2 | 공정별 자료가 없거나 다기능 공정이면: 열(A.2.2)·폐가스(A.2.3)·화학물질 몰비(A.2.1)를 빼고는 **「생산된 개별 재화의 기능단위」 기준으로 귀속한다.** 적용 순서는 열 → 폐가스 → 기능단위 |
| 부속서 III A.3 | 식 55(직접)·56(간접)·57·58. 측정가능열을 만드는 연료가 둘 이상의 생산공정에 쓰이면 그 연료 배출은 공정의 직접배출(DirEm*)에 넣지 않고 EmH,imp(쓴 열량 × 열 배출계수)로 귀속한다 |
| 부속서 II F | 활동수준(분모)은 판매 가능하거나 전구물질로 쓰이는 재화만. 불량·부산물·폐기물·스크랩은 제외하고 배출 0 |
| 부속서 II A.5 · 부속서 IV | 귀속 방법은 모니터링 계획과 운영자 보고서에 적는다 |

### 앱에 이미 있는 것

- 한 공정 안 여러 제품 → 생산량(질량) 비율로 자동 배분. 사용자 지정 배분은 「규정 예외」로 다뤄 사유·증빙을 요구하고, 합계가 100%가 아니면 차단 경고 (`calculation-engine.ts`, `allocation-rules.ts`의 `CBAM-ALLOC-MANUAL-01~03`)
- 스크랩·불량 라인 제외(배출 0, 분모 제외). 비CBAM 공동산출물 라인은 「정규 제품인지 부산물인지」 확인 요구 (`CBAM-ALLOC-AL-01`)
- 연료 공용 계량기: 보조계량기 행은 정합계수 자동 적용, 배분키 행은 합계 = 전체 검사 (`reconcileSourceStreams`, `CBAM-ALLOC-RECF-01·02`) — **입력 화면은 상세 화면 `/source-streams`에만 있다**
- 같은 CN을 같은 기간에 공정 2개 이상으로 나누면 경고 (`CBAM-ALLOC-ROUTE-01`)
- 구매 강재의 제품별 귀속(생산량 비율 자동 / 제품별 직접 입력 + 합계 검사), 사내 이송, 밖에서 산 스팀·온수
- 산정보고서가 배분 기준·직접귀속배출 산정방식·정합계수·전력 배분 근거를 싣는다

### 보완할 곳 (우선순위 순)

1. **나누는 계산을 앱이 하지 않는다.** 담당자가 엑셀로 몫을 계산해 공정마다 따로 적는다(예시 자료의 24,459 Nm³ = 38,500 × 3,240/5,100은 사람이 계산한 값). 기본 화면인 지도 4단계에는 공용 계량기 입력이 없다.
2. **전력에는 구조가 없었다 → 2026-10-05 구현·머지(PR #84, `CBAM-ALLOC-ELEC-01`).** 지도 5단계 위쪽의 「전력 나누기」가 공장 전체 값과 기준을 받아 공정별 몫을 계산해 적고, 엔진이 합계를 계속 검사한다. 나눈 값은 저장할 때 `electricity_mwh`에 들어가므로 엔진 산술·EU 문서·보고서·백업 형식은 그대로다(`src/lib/electricity-allocation.ts`, `src/components/guided/ElectricitySplit.tsx`, `scripts/verify-electricity-allocation.mjs`). 기준은 아래 3번 판정대로 셋만 둔다 — 계량기 값 / 생산량 / 간접결정 추정.
3. **배분키의 규정 근거 — 원문 대조 판정(2026-10-05).**
   - 생산량(기능단위) 배분은 「허용」이 아니라 **자료가 없을 때 규정이 지정한 방법**이다(부속서 III A.2 둘째 단락 "shall be attributed based on the functional unit").
   - 운전시간·정격용량을 **비율로만** 쓰는 배분키는 2025/2547에 근거가 없다. 앱의 `CBAM-ALLOC-RECF-02`가 이를 「규정상 허용 · A.2」로 부르는 것은 틀렸다 — **고쳤다(PR #85)**(연료 공용 계량기 `SourceStreamSharedMeter.basis`, `SHARED_METER_BASIS_LABEL`, 보고서 문안).
   - 길은 하나 있다: 정격용량 × 가동시간(× 부하율)으로 **공정별 사용량 자체를 추정**하면 부속서 II A.3(2)(b)·(c)의 간접결정방법이다. 그러면 「자료가 있는 경우」(부속서 III A.1)가 되어 추정 합계를 사업장 계량값에 맞춘다. 조건: 직접 계량이 기술적으로 불가하거나 비용이 과다하다는 사유를 모니터링 계획에 적고(A.3(7)·(8)), 상관식은 연 1회 타당성을 평가하며(A.3(2) 끝 문단), 해마다 같은 방법을 쓴다(A.2(2)).
   - 검증 관점: 방법이 규정과 다르면 부적합(non-conformity)이다. 제품 1톤당 SEE의 5%가 중요성 기준(2025/2546 Article 5(1))이라 가공업체의 자체 에너지 몫(예시 자료 약 0.6%)에서는 중요한 왜곡이 되기 어렵지만, 검증인은 크기와 성격으로 판단할 수 있고(Article 5(2)) 개선 권고 대상이 된다.
4. **사내 공용 보일러(스팀·온수) — 원문 대조 판정(2026-10-05).**
   - 스팀·온수가 측정가능열(배관으로 옮기는 열매체, 열량계를 달 수 있음 — 정의 29)이고 **둘 이상의 생산공정**(또는 공정 밖 용도)에 쓰이면, 그 연료 배출은 공정의 DirEm*에 넣지 않고 **쓴 열량 기준**으로 귀속해야 한다: 부속서 III A.3의 DirEm* 정의("…or which is used in more than one production process … added under the parameter EmH,import"), EmH,imp 정의("a technical unit … that supplies heat to more than one production process"), A.2.2 식 44, A.2의 적용 순서 (1) 열. 의무 규정이다.
   - 공정별 열량은 계측(방법 1) → 연료투입 × 측정효율(방법 2) → 연료투입 × 70%(방법 3) 순으로 정하고(부속서 II C.1.2), 공정별 계측이 없으면 간접결정방법으로 나눈다(부속서 II A.3(2)가 이 경우를 직접 든다). 열 손실은 열을 쓰는 공정에 비례로 얹어 100%를 귀속한다(A.2.2 끝).
   - 앱의 현재 방식(보일러 연료를 배분키로 나눠 DirEm*에 넣음)과의 차이: 사업장 합계는 같다. 달라지는 것은 ① 공정별 몫(생산량 비율 ≠ 열 사용 비율일 때) ② EU 문서에서 적히는 자리(DirEm*가 아니라 열 수입 칸) ③ CBAM 공정 밖에서 쓴 열(사무동 난방·비대상 제품)을 뺄 수 있다는 점이다.
   - 해당하지 않는 경우: 한 공정만 쓰는 전용 보일러(연료가 그대로 DirEm*), 직화 가열로처럼 열매체가 없는 비측정가능열(공용이면 A.1·A.2로 나눔).
   - 남는 불확실성: 세척수처럼 온수를 열매체가 아니라 공정수로 직접 소비하는 설비를 측정가능열로 볼지는 설비 구성에 따라 갈릴 수 있다 — 사업장별 판단.
   - **구현·머지함(2026-10-05, PR #86, `CBAM-ALLOC-HEAT-02`).** 지도 4단계 위쪽 「열 공급원 만들기」: 보일러 연료를 어느 공정에도 매지 않고 모아, 공정별 열 사용량(계측·연료투입×효율·추정)과 공정 밖 사용량(사무동 등)의 비율로 귀속한다. 소비처 + 공정 밖 = 연료 배출 전체(누락·이중계상 없음). 귀속분은 기존 EmH,imp 칸에 합산되고, EU 문서에는 같은 D_Processes 열 수입 칸(L+46·L+47)에 적는다. 열량 비율의 분모는 EU 문서에 안 나가는 공정까지 **전체 공정**이다.
   - 예시 시험(대일기업, 가정: STS 3,000 Gcal · 탄소강 750 Gcal): 보일러 79.91 tCO₂e → STS 63.93(80%) · 탄소강 15.98(20%). 종전(생산량 비율 63.5 : 36.5)은 STS 50.77 · 탄소강 29.14. STS 기준 SEE 3.764 → 3.768(+0.1%).
   - 열 손실을 따로 재지 않으면 연료 배출 전체가 소비처에 비례로 얹힌다 — 「손실은 열을 쓰는 공정에 비례로 얹어 100%를 귀속한다」는 규정(A.2.2 끝)과 같은 결과다. 열 손실을 따로 계측하는 사업장은 그 값을 넣는 칸이 아직 없다.
5. **부속서 II A.4 안내·검사가 없다.** 크기·형상만 다른 철강 제품을 CN별로 공정을 따로 만들어 에너지를 임의로 나누는 것을 막지 못한다.

3·4의 판정은 공인 검증인의 결정이 아니라 원문(2025/2547·2025/2546)을 조항 단위로 대조한 분석이다. EU 집행위의 확정기간 지침서가 나오면 그것으로 다시 확인한다.

## 12. 전구물질 · 출처 표시 · 산출물

### 전구물질 처리

담당자가 가장 크게 막히는 지점. 여기서 앱이 손을 놓으면 그날 작업은 끝난다.

- 기본값으로 먼저 계산을 완료시키고, 실제 값이 오면 교체 — **[v4] 이미 있다**(`panels.tsx` PrecursorPanel의 「EU 기본값 채우기」, 실측-기본값 비교)
- 앱이 필요 항목을 이미 알고 있으므로 **공급업체 요청 양식 자동 생성 → 내보내기** — [v4] 없다. 재료(전구물질 후보, CN, 소비량, `src/lib/docx-builder.ts`)는 다 있다
- 회신 파일 재업로드 시 해당 값만 갱신 → 지도 노드 빗금 해제, 막대 블록 실색화, 실측 비율 상승이 연쇄적으로 재생 — [v4] 표준 양식(EU Communication Template) 회신은 룰 파싱(§7)

### 값의 출처 표시 (검증 대응)

모든 값에 상태 태그: **실측 / 기본값 / AI 추정(미확정) / 미입력**. 지도 노드 패턴, 막대 블록 패턴, 표 셀 배경이 **동일한 시각 규칙**을 공유한다. 최종 보고서에도 출력되어 검증 시 근거 자료가 된다.

**[v4]** 데이터 모델에 이미 있다 — 전구물질 `data_mode`(ACTUAL / SEMI_ACTUAL / DEFAULT)와 `verification_status`, 배출원 `factor_source_type`, 전력 계수 출처. 산정보고서도 이미 전구물질별 "데이터 구분(실측 / 혼합 / 기본값)"을 싣는다. SEMI_ACTUAL(혼합)을 어느 태그로 보일지는 미결(§13).

### 산출물

마지막 화면이 곧 결과물. CBAM 커뮤니케이션 템플릿 자동 기입, 산정 보고서, 근거 데이터 일체. 담당자에게 이 앱의 존재 이유는 배출량 숫자가 아니라 **보낼 수 있는 파일**이다.

| **새 UI** (지도에서는 「이전 화면」 버튼) | `modern` | `BeginnerAppShell` — 녹색 사이드바 5메뉴 + 7개 라우트에 `Beginner*` 간단 화면 | 7월 중순 이후 사실상 방치. `verify:beginner-ui`는 `npm run verify` 체인에 없다 |
| **이전 버전** | `previous` | `ModernAppShell` — 사이드바 14메뉴 + `ModernDashboard`·`ModernProducts` | 방치 |
| (버튼 없음) | `legacy` | `LegacyShell` | 들어가는 길이 없다 — 옛 저장값이 남은 브라우저에서만 뜬다 |

- 이름이 상대적이라 헷갈린다: 「새 UI」가 지도 화면보다 **오래됐고**, 지도의 「이전 화면」 버튼이 가는 곳이 다른 화면들이 「새 UI」라고 부르는 그 화면이다.
- **옛 화면에는 지도에서 고친 결함이 남아 있다.** 예: `BeginnerPrecursors.tsx`는 공급국가를 아직 'South Korea'로 미리 채우고 저장 때도 그 값으로 떨어진다(지도 패널에서는 run11 P0-04로 "앱이 대신 정하지 않는다"로 고쳤다). 지도에서 옛 화면으로 넘어간 사용자는 이미 고친 결함을 다시 만난다.
- 제품군 프리셋·일괄 입력은 공유 상세 화면(`src/app/products/page.tsx`)에 있고, 지도는 모든 상세 화면으로 가는 링크를 갖고 있다 → 옛 셸을 숨겨도 **없어지는 기능은 없다**(옛 셸 고유의 것은 같은 자료를 보는 다른 첫 화면·간단 화면뿐. 단, `Beginner*` 화면을 기능 단위로 전수 대조하지는 않았다).
- **컨셉과의 관계**: 세 화면은 "초보자용 vs 전문가용"이라는 같은 질문에 세 번 답한 흔적이다. 컨셉은 이것을 **화면 하나 + 축**으로 답한다 — 「새 UI」가 하려던 일(초보자용 간단 화면)은 입문자 모드와 대화형이, 「이전 버전」이 하던 일(전체 메뉴)은 지도의 백스테이지와 실무자 모드가 이어받는다. 컨셉 구현은 네 번째 UI를 만드는 것이 아니라 **지도 화면의 다음 버전**이다.

## 14. [v4] 구현 원칙 — 고생해서 만든 앱을 망가뜨리지 않기

지킬 자산: ① 산정 엔진 ② EU 템플릿 Export ③ 산정보고서 ④ 데이터 모델·`.cbam` 백업 호환성 ⑤ 지도 패널에 들어간 결함 수정들과 검증 스크립트. **컨셉은 ①~④를 건드리지 않는다.**

1. **추가만 하고 수정은 하지 않는다.** 새 기능은 새 파일로. `calculation-engine.ts`, `eu-template-export.ts`, `calculation-report.ts`, `local-db.ts`의 스키마를 고쳐야 하는 상황이 오면 **멈추고 사용자에게 먼저 묻는다.**
2. **`panels.tsx`를 "질문 스키마"로 뜯지 않는다.** 그 안에 "대만 기본값이 한국 값으로 들어감", "다른 공정 값이 이 공정에 저장됨", "스크랩 라인에 원료가 배분됨" 같은 수정이 수십 개 들어 있고, 검증 스크립트가 소스를 글자 그대로 읽는다. 원안의 "기존 8단계 로직을 질문 단위로 분해"는 **하지 않는다.**
3. **대화형 모드는 옆에 새로 짓는다.** 자체 저장 코드를 두지 않고 `guided-edit.ts` 등 기존 순수 빌더만 거친다 — "동일 스키마 공유"를 화면이 아니라 저장 로직 층에서 달성한다. 새 파일에도 `verify-guided-panels.mjs`와 같은 구조 검사를 건다.
4. **막대·맵은 자체 산술 금지.** `SeeFlowBinding`과 `describeSeeFlowIndirect`만 읽는다.
5. **옛 UI 셸 3종은 삭제하지 않고 숨김·동결.** 3축 모드는 guided 셸에만 적용한다(안 그러면 검증 조합이 8×4). 숨길 때는 **지도에서 옛 화면으로 나가는 버튼만 없앤다** — 옛 화면에서 지도로 돌아오는 버튼은 남겨야, 옛 모드 값이 저장된 브라우저의 사용자가 갇히지 않는다.
6. **내장 EU 기본값은 대체용.** 사용자가 올린 공식 파일이 항상 우선. 내장값에는 기준일을 표시. 기존 업로드 흐름은 그대로.
7. **단계 하나 = PR 하나.** `npm run verify` 통과 후 머지. 입력 경로를 건드린 단계는 머지 뒤 씨밤이 회귀 1회.
8. **기본 경로는 끝까지 지금의 지도 화면.** 대화형은 별도 진입로로 두고, 검증이 끝나기 전에는 기본값으로 올리지 않는다(`/cockpit-preview/easy-mode`를 원본을 건드리지 않고 시험한 것과 같은 방식).
9. **언제든 되돌릴 수 있게.** 덧붙인 것이므로 연결만 끊으면 원래대로 돌아가야 한다.

## 16. 미결정 사항 (사용자 결정 또는 확인 필요)

1. **AI API 비용 부담 주체**와 키 방식(무상배포 앱에서 운영자 부담 / 사용자 키 / 유상판 전용).
2. **직접배출만 해당하는 품목의 간접배출 보고가 법적으로 필수인가** — 화면은 "입력 필수", 근거 문서(`docs/harness/cbam-2026-definitive-basis.md`)는 "증빙·검토·템플릿 기재에 유용". 규정 확인 필요. 결과에 따라 대화형에서 전력 질문을 건너뛸 수 있게 할지가 갈린다.
3. **대화형 모드 진행 여부**는 5단계까지 해본 뒤 결정.
4. ~~내장 EU 기본값의 범위~~ — 결정됨: 일부만 넣으면 대만 같은 국가가 조용히 비므로 공식 워크북 전체(115개국·전 CN)를 넣었다(압축 시 약 120KB). 새 판이 나오면 `npm run generate:bundled-references`로 다시 만든다.
5. **SEMI_ACTUAL(혼합) 자료의 출처 태그** 표시 방법.
6. **시각 토큰 조정** — 단색 명도 계열 요구 vs `DESIGN.md` teal 토큰·`verify:design-system`.
7. ~~막대 위치~~ — 결정됨: 2열 레이아웃의 왼쪽(지도) 칸 안, 지도 바로 아래. 오른쪽 패널은 스크롤에 따라 고정이라 같은 화면에서 입력과 막대를 함께 본다.
8. **옛 셸 숨김 시점** — 작업 순서상 5단계에 들어 있으나, 옛 화면에 고친 결함이 남아 있으므로(§13) 컨셉 작업과 무관하게 맨 앞으로 당길 수 있다(버튼 하나를 숨기는 작은 변경). 앞당길지는 사용자 결정.
9. **배분 규정 판정 2건의 후속 조치**(§8-1의 3·4) — ① 연료 공용 계량기의 운전시간·정격용량 키를 「추정 사용량(간접결정)」으로 다시 분류할지 ② 사내 공용 보일러의 열량 기준 귀속을 구현할지(엔진·EU 문서 변경). 둘 다 사용자 결정.
10. **「나누기」 단계의 나머지** — 전력은 구현했다(§8-1의 2). 연료 공용 계량기를 지도 4단계에서 같은 방식으로 나누는 것, 목업 2-1처럼 고지서 단위로 한 화면에 모으는 것은 아직이다.
