# 공정 간 전가(사내 전구물질) 설계안

- **작성일**: 2026-09-19 · main @eb05b27
- **상태**: 0~4단계 구현 완료(2026-09-19). 아래 「진행 기록」 참조. §7의 결정 항목은 모두 제안대로 진행했다.
- **계기**: 두 번째 시험 원장(동성특수강, `cbamy/runs/2026-09-19_run15-ledger2/`). run08에서 처음 보고됨.

## 쉽게 말하면

제강 공정(P1)이 만든 슬래브의 일부를 같은 공장의 압연 공정(P2)이 받아 제품을 만든다. 슬래브를 만들 때 나온 배출은 압연 제품에 실려 가야 한다. 지금 앱은 이 연결을 하지 않는다. 그래서 압연 제품의 SEE가 **0**으로 나오고, 경고 한 줄만 뜬 채 EU 문서가 만들어진다. 사용자가 P1 결과를 보고 P2에 「구매 전구물질」로 손으로 다시 넣어야 하는데, P1 값이 바뀌면 또 고쳐야 하고, 그렇게 넣으면 EU 문서에서는 이중으로 계산된다(§2).

## 1. 규정이 요구하는 것

Implementing Regulation (EU) 2025/2547 (영문 원문 확인).

| 조항 | 내용 |
|---|---|
| 제4조 9항 | 복합제품의 전구물질을 같은 사업장에서 만들고, **그 전구물질을 판매하거나 다른 공정에 쓰려고 내보내지 않으면**, 전구물질과 복합제품을 하나의 공동 생산공정으로 묶어도 된다. 이때 배출은 함께 모니터링·산정한다. |
| 부속서 III, 전구물질 자료 (1) | 전구물질을 사업장 안의 **다른 생산공정**에서 만들면 다음을 정한다: (a) 그 전구물질의 직접·간접 SEE — **보고기간 평균**, tCO₂e/t, (b) 사업장의 **각 생산공정에서 쓴 양**. |
| 부속서 IV 보고 항목 18·19 | 사업장에서 만들어 사업장이 쓴 전구물질의 양(종류별), 각 생산공정에서 쓴 양. 제4조 9항으로 묶은 것은 제외. |

동성특수강은 슬래브의 45%를 **시장에 판다**. 그래서 제4조 9항(공정 묶기)을 쓸 수 없고, 부속서 III (1)의 사내 전구물질로 처리해야 한다. 슬래브를 전혀 팔지 않는 사업장이라면 공정을 하나로 묶는 것이 허용되고, 앱에서는 공정 하나로 입력하면 된다(지금도 가능).

## 2. EU 템플릿은 이미 이 계산을 한다

Communication Template의 `D_Processes`에는 공정마다 다음 칸이 있다.

| 항 | 칸 | 뜻 |
|---|---|---|
| (a) | L16~L24 | 총 생산량 (= SEE 분모) |
| (b) i | L27 | 시장 출하량 |
| **(c) 1~9** | **L32~L40** | **사업장 안의 다른 생산공정에서 소비된 양 — 받는 공정별로 한 칸씩** |
| (d) | L41 | 비CBAM 재화에 소비된 양 |
| (e) | L42 | 검산 (= (a) − (b) − (c) − (d), 0이어야 함) |

(c)의 칸은 **자기 자신을 뺀 다른 공정**이 순서대로 놓인다. 공정 1의 첫 칸은 공정 2, 공정 2의 첫 칸은 공정 1이다. 받는 공정별 양만 적으면 템플릿의 수식이 상류 공정의 SEE를 하류 공정에 얹는다.

공식 예제 `3 CBAM SEE V2.1_Example Steel 2 EAF alloys_final.xlsx`가 같은 구조다.

| | 값 |
|---|---|
| 공정 1 (EAF) 총 생산 | 2,234,000 t · 시장 1,007,000 t · (c)1 「Rolling mill and finishing」 1,227,000 t |
| 공정 2 (압연) 총 생산 | 1,133,000 t · 전량 시장 |
| Summary_Products — 조강 72189911 | 직접 1.0015 · 간접 1.3784 |
| Summary_Products — 압연재 72191310 등 | 직접 **1.4396** · 간접 1.7315 |

이 예제는 **정답지**로 쓸 수 있다(§6).

### 지금 앱이 하는 것

- 엔진은 `internal_consumption_mass_t`를 **계산에 쓰지 않는다**. EU 문서에만 적는다.
- 내보내기는 그 합계를 `L32`(첫 칸)에 적는다. 공정이 둘이면 우연히 맞지만, 셋 이상이면 받는 공정이 누구인지와 상관없이 첫 칸에 몰린다.
- **우회 입력은 EU 문서에서 두 배로 계산된다 (2026-09-19 Excel 재계산으로 확인).** 사내 이송분을 「구매 전구물질」로 넣으면 `E_PurchPrec`에도 실리고 `D_Processes` (c)에도 실린다. 템플릿은 두 경로를 다 더한다. 두 번째 시험 원장의 2026년 EU 사본을 Excel로 재계산한 결과:

  | 제품 | 앱 (직접) | Excel 재계산 (직접) |
  |---|---|---|
  | 슬래브 72189911 | 1.1364 | 1.136 |
  | 평판재 72191310 | 1.2307 | **2.461** (= 1.2307 × 2) |

  앱 화면의 숫자는 맞아 보이기 때문에 알아채기 어렵다. **지금 우회 입력을 쓰고 있는 사용자의 EU 문서는 하류 제품 SEE가 두 배다.** run08 이후 안내해 온 우회로가 문서 단계에서는 틀렸다는 뜻이다.

## 3. 자료 모델

새 저장소 하나를 둔다.

```ts
// store: internal_transfers
interface InternalTransfer extends LocalEntity {
  period_id?: string;
  /** 만든 공정 */
  source_process_id: string;
  /** 어느 제품 라인의 산출물인가 — 다제품 공정에서 SEE가 라인마다 다르다 */
  source_output_line_id?: string;
  /** 받은 공정 */
  target_process_id: string;
  /** 받은 공정이 이 기간에 **소비한** 양 (t) — 부속서 III (1)(b) */
  mass_t: number;
  note?: string;
}
```

왜 공정의 필드가 아니라 별도 레코드인가: 한 공정이 여러 공정에 넘길 수 있고(템플릿은 9칸), 받는 공정마다 양이 다르다. `internal_consumption_mass_t`는 **파생값**(= 이 공정에서 나간 이송량의 합)으로 바꾼다. 종전 자료에 값만 있고 이송 레코드가 없으면 「받는 공정을 지정하세요」 경고를 낸다.

전구물질(`precursors`)에 끼워 넣지 않는 이유: 구매 전구물질은 공급국·검증상태·기본값 같은 필드가 핵심인데 사내 이송에는 전부 해당이 없다. 그리고 `E_PurchPrec`에 실리면 안 된다(§2).

백업 형식: 저장소가 하나 늘어난다. `format_version`은 1로 두고 `stores`에 없으면 빈 배열로 읽는다(기존 백업 호환). 새 백업을 옛 앱에서 열면 이송 레코드가 무시된다 — 하류 SEE가 다시 0이 되므로, 옛 앱이 남아 있을 가능성이 있으면 `format_version`을 2로 올려 거부하게 하는 편이 안전하다(§7-4).

## 4. 계산

지금은 공정마다 독립으로 계산한다. 이를 **두 단계**로 나눈다.

1. **자체 몫**: 공정별로 지금처럼 계산한다 — 직접(배출원), 간접(전력), 구매 전구물질. 변경 없음.
2. **사내 전가**: 공정을 상류에서 하류 순으로 돌면서, 받는 공정에 다음을 더한다.

```
받는 공정 p의 사내 전구물질 배출(직접)
  = Σ_이송 t→p  mass_t × SEE_직접(보내는 라인)      ← 보내는 쪽의 **최종** SEE (자체 + 구매 + 그 위 사내)
간접도 같은 식으로 따로.
```

- **순서**: 이송 레코드로 방향 그래프를 만들고 위상 정렬한다. 상류의 최종 SEE가 정해진 뒤에 하류를 계산한다.
- **순환**(A→B→A): 실제 공장에 있을 수 있다(스크랩 회수 등). 1차 구현은 **지원하지 않고 차단 오류**로 알린다. 규정은 연립방정식 풀이를 요구하지 않고, 템플릿도 순환을 풀지 않는다. 필요해지면 반복 수렴으로 확장한다.
- **기간**: 보내는 공정과 받는 공정이 같은 기간이어야 한다. 다르면 오류.
- **SEE는 기간 평균**(부속서 III (1)(a)): 보내는 라인의 그 기간 SEE 하나를 쓴다. 재고 이월은 다루지 않는다.
- **분모는 바뀌지 않는다**: 보내는 공정의 SEE 분모는 지금처럼 총 생산량(시장 + 사내 이송)이다. 템플릿 (a)와 같다.
- **기준 SEE / 검토용 총 SEE**: 철강은 간접이 인증서 기준에서 빠진다. 사내 전가분도 직접은 기준에, 간접은 검토용에만 들어간다. 구매 전구물질과 같은 규칙.
- **결과 필드**: `internal_precursor_direct_see`, `internal_precursor_indirect_see`, `internal_precursor_inputs[]`를 새로 둔다. 구매 전구물질 필드와 합치지 않는다 — 산정보고서와 화면이 둘을 따로 보여줘야 한다.

### 검산

- 보내는 공정: 시장 출하 + Σ 사내 이송 + 비CBAM 소비 = 총 생산량. 어긋나면 지금의 「시장+내부≠총량」 오류를 그대로 쓴다(템플릿 (e)와 같은 검사).
- 받는 공정: 받은 양의 합이 그 공정의 산출량보다 **작으면** 경고(수율 100% 초과는 물리적으로 이상). 동성특수강은 1,227,000 t 투입에 1,133,000 t 산출(수율 92%)로 정상.

### 무상할당 조정(SEFA)

2025/2620 부속서 식 (4)의 전구물질 몫에 사내 전구물질도 들어간다. 3.3(1)은 「생산자가 제공하고 검증된 값」을 쓰라고 하는데, 사내 전구물질은 **같은 사업장의 같은 검증 범위**이므로 보내는 라인의 SEFA를 그대로 쓴다(B열 기본값이 아니라). 지금 우회 입력에서는 슬래브 B열 1.189가 통째로 적용돼 평판재의 SEFA(1.3266)가 SEE(1.2307)보다 커지는 이상이 있다. 이 설계로 해소된다.

## 6. EU 문서 내보내기와 검증

- `D_Processes` (c) L32~L40: 받는 공정의 **템플릿상 순번**(자기 자신을 뺀 순서)에 맞는 칸에 양을 적는다. 지금처럼 합계를 첫 칸에 몰아 적지 않는다.
- 사내 이송은 `E_PurchPrec`에 적지 않는다.
- 비CBAM 공정이 받는 경우: 템플릿에는 그 공정이 없으므로 (d) 「비CBAM 재화에 소비」 L41에 적는다.
- **정답지 검증**: 공식 EAF 예제의 입력을 앱 자료로 옮긴 고정 자료(fixture)를 만들고, 앱 엔진의 결과가 예제의 Summary_Products(조강 1.0015 / 1.3784, 압연재 1.4396 / 1.7315)와 맞는지 검증 스크립트로 잠근다. 그다음 앱이 만든 EU 사본을 Excel로 재계산해 같은 값이 나오는지 확인한다(`docs/excel-recalculation-review.md`의 절차).

### 개발 시 주의 — DB 버전

DB가 v6으로 한 번 올라간 브라우저 프로필은 v5 코드(이 변경 이전의 브랜치)에서 열리지 않는다(IndexedDB VersionError). 시험 원장이 든 프로필로 옛 브랜치를 돌려야 하면 프로필을 복사해서 쓴다. 1단계의 업그레이드 확인도 복사본으로 했다.
