## 2. 사업장 집계 — 두 값을 반드시 분리한다

생산량 가중(3,400,000 t 기준):

| | 값 |
|---|---|
| `see_cbam_basis` (인증서 산정 기준) | **0.188** (0.18830525) |
| 간접 SEE | 0.020 (0.02026765) |
| `see_informational_total` (검토용 총 SEE) | **0.196** (0.19641231) |

### 이 집계에서 항등식은 성립하지 않는다

```
0.188 + 0.020 = 0.209  ≠  0.196
```

제품마다 간접분의 인증서 반영 여부가 다르기 때문이다. 소결광의 간접분은 이미 기준 안에 있고
강관의 간접분은 밖에 있다. 두 제품을 합친 자리에서 「총 SEE = 기준 + 간접」이라 쓰면 거짓이 된다.

**앱은 이 자리에 집계 SEE 줄을 두지 않는다.** 7단계 화면도 이렇게 말한다:

> 제품마다 간접분의 인증서 기준 반영 여부가 달라, 기준 SEE와 총 SEE의 관계를 한 줄로
> 말할 수 없습니다 — 제품별 결과를 확인하세요.

보고서에도 집계 SEE 행이 없다. 구조적으로 틀린 등식을 쓸 자리가 없는 것이 옳다.

## 3. 이번 run에서 달라진 것 — 숫자가 아니라 라벨

run09에서 0.2066은 **표에서는 「CBAM 기준 SEE」, 세 줄 아래 각주에서는 「참고·정보 목적」**이었다.
같은 숫자를 한 문서가 두 가지로 불렀고, 각주를 믿은 검증인은 소결광의 기준을 0.1929로 읽어
**7.4% 과소 적용**하게 된다.

지금은 이렇게 나온다:

> 총 SEE(직접+간접) = ERW 강관 0.1198 (정보 목적 — 인증서 기준 제외) ·
> 소결광 (Sintered Ore) 0.2066 (**= CBAM 인증서 산정 기준**) tCO2e/t.

10장 총 SEE 행도 「직접 + 간접 = CBAM 인증서 산정 기준」으로 표기되고,
5.4장이 두 품목의 기준 산식을 각각 제시한다.

## 4. 반올림 — 앱이 맞고 계산기가 틀리는 자리

소결광 직접 SEE의 정확값은 `578,550 ÷ 3,000,000 = 0.19285`다. 소수 4자리 반올림은 **0.1929**.

JS `(578550/3000000).toFixed(4)`는 **0.1928**을 준다 — 0.19285가 이진 부동소수점에서
0.19284999…로 저장되기 때문이다. 앱의 `roundForReport`는 이 오차를 제거한다.

검증인이 스프레드시트나 계산기로 검산하면 앱 값이 맞는다. 다만 **JS 계산기로 검산하면
마지막 자리가 다르게 보일 수 있으므로**, 이 자리는 검증 대응 시 설명이 필요하다.
